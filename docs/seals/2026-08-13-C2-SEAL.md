## Addendum 2026-08-14 — Lane E triage of the inherited findings

The record above is preserved verbatim. The entries below are corrections found
while fixing the findings; they are appended rather than edited into the text,
because the seal is a historical record of what was believed at seal time.

**Finding 1 — CLOSED BEFORE THE SEAL, entry is stale.**
`write_welcome_supersessions_with_cursor` does insert the recovery work item.
Its Expired arm requires `disposition.recovery_work_id` (erroring
`MissingContext` when absent) and unconditionally calls
`delivery::insert_recovery_work_item`. `terminalize_prior_bound_welcome_expiry`
has exactly one caller, so there is no second path. The fix landed in
`0c6290a0`, which is an ancestor of the seal commit `1ffea8d3` — the code was
already correct when this doc was written. No Lane E change was required.

**Finding 5a — headline inaccurate; a different real bug lives in that function.**
"Every production read of a closed conversation fails Invariant" describes a
defect in `authorize_conversation_state` that C2 itself fixed (see this seal's
own fix list, "closed conversations 500 instead of deny"). A closed conversation
now exits at `classify_current_relationship` with a typed denial and never
reaches the interval loader. Separately, `build_ordered_interval_witnesses` did
carry a real defect, with a different blast radius: it rejected
`start_seq <= previous_terminal`, but `chat.assert_application_interval_schedule`
treats only `terminal_seq > start_seq` as overlapping and MANDATES the touching
boundary for replace->add and reset->reset. It therefore over-rejected every
reset activator and every leaf-recovery-replaced device — not closed
conversations. Latent while no read endpoint is wired. Fixed in Lane E.

**Finding 2 — real, and the reachable half is not the half described.**
The prewrite asymmetry is genuine but not attacker-drivable: `parse_metadata_snapshot`
already enforces the ciphertext/digest invariants and a CHECK constraint
backstops the table. The client-reachable defect is adjacent —
`assert_metadata_snapshot_mapping`'s commit arm pins `ciphertext_size` forward,
while `commit_metadata_matches` never checked ciphertext length, so a
validly-signed re-encryption of a different length passed planning and failed in
the deferred trigger at COMMIT as a 23514 storage 500. Fixed in Lane E.

**Findings 3, 4 and 5b — confirmed open, not fixed in Lane E.** See the Lane E
report for the analysis, in particular that finding 3's rejection is structural
(only the Request endpoint can mint `SealedResetTerminal::Expired`) and that
5b is a contradiction between two `#[ignore]`d tests and the frozen spec, which
needs a design ruling rather than a mechanical fix.

**Suite counts.** The seal's counts reproduce exactly at `425e149f`, but ONLY
with the frozen crypto-wire corpus reachable at
`<parent-of-mls-ds>/docs/generated-artifacts/mls-chat-v1/crypto-wire`. That path
escapes the repository, so without it `chat_protocol_executor` fails to COMPILE
(producing no `test result:` line at all), `chat_protocol_snapshot` is 0/10 and
`chat_protocol_state_machine` is 102/40. See the Lane E report's corpus-durability
proposal.

## Addendum 2026-08-14 (second) — Lane E outcomes at stand-down

Appended, not edited, for the same reason as the first addendum. This records
what is true when the founding Lane E agent stood down; the finding-3 entry is

**Finding 5b — SETTLED ON THE SPEC, by ruling.** Josh ruled the two
`entry_intervals_*` tests be excised in favour of the model the frozen spec,
the `authorize_entries` doc, BREAD-05 and the passing sibling
`former_exact_device_gets_access_outside_membership_interval` all encode. Taken
as the rewrite option rather than deletion, because the fixtures supported it:
the removed device and the post-reset old device now assert the
`AccessOutsideMembershipInterval` denial, and the properties those tests were
named for moved to devices that actually hold an interval. Verified by

failed, both on `AccessOutsideMembershipInterval`. After: 2/2, with the full
ignored set 20/0 in the same run, so the contradiction is resolved rather than
relocated. Sealed `01abbd7f`.

**Finding 5a — the touching boundary, with a production-path lock.** Sealed
`330475eb`. In addition to the pure validator tests, the reset ACTIVATOR arm of
`entry_intervals_preserve_readd_gaps_and_generation_boundaries` now reads
through the production path: that device's retired interval closes `reset` at
the activation sequence while its successor opens at the SAME sequence, which

**Finding 2 — sealed `47f8d99b`,** with the RED verified (removing the single

**Finding 3 — RULED, BLOCKED, HANDED OVER. Not fixed.** The seal's
classification of "inconsistency, not a wedge" is wrong: it is a permanent,
conversation-wide loss of reset capability, because `seal_pending_reset` is
composed unconditionally by BOTH endpoints, so a revoked or rebound original
requester kills the `requestReset` rescue path inside the same seal that blocks
`activateReset`. Josh ruled BOTH fixes — (b) `revokeDevice` terminalizes the
revoked principal's pending resets, and (a) a lapsed-row disposal route bound to
recorded authority and the immutable signed bytes rather than live device state
— with the hard constraint that **`activateReset` keeps FULL strict
live-authority verification; the relaxation is expiry/disposal only**, and no
sweeper may compose the existing seal.

Not implemented here. The ordered DB-backed reproduction, which is also the
acceptance evidence, cannot run: `chat.reset_requests` is EMPTY in the test
database and all 17 `#[ignore]`d tests in `chat_protocol_reset_repository.rs`
fail at `:601` on the absent ALICE fixture corpus. Landing authority changes
with no executable acceptance test was refused. See
`docs/seals/2026-08-14-LANE-E-HANDOFF.md` for the trace, the blocker evidence,
the scouted unblock and the ratified repro shape.

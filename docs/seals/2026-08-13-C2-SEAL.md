## Addendum 2026-08-14 (third) — Finding 3 reproduced, fix (a) shipped, fix (b) blocked

### The blocker in the second addendum is gone

`chat.reset_requests` really was empty (re-verified by direct query, not
inherited), so the reproduction needed a fixture that did not exist.
`seed_private_genuine_pending_reset` stops the existing dynamic sequence one step
before `commit_dynamic_reset_activation`, leaving a genuine, live, PENDING row in
a self-bootstrapping per-run database. The shared database is never seeded.
Sealed `6f79addc`, together with `tests/chat_protocol_reset_wedge.rs` — a new
target, because neither existing harness could host the proof:
`chat_protocol_reset_repository.rs` includes `reset.rs` but draws fixtures from
the shared database, while every harness carrying `common/executor_seed.rs` lacks
`reset.rs`.

### The wedge is reproduced

Sealed `ae7980b0`. `DeviceOrKeyDrift` for BOTH `ResetPreparationKind::Request`
and `::Activation`, on BOTH ruled triggers (requester revoked; requester rebound
with an `auth_generation` bump), for a principal that never touched the row AND
for the original requester — `load_locked_pending_row` selects by
`conversation_id` alone, so the row is unsealable by anyone. A control proves the
undrifted fixture seals fine, so the failures are caused by the trigger rather
than the probe. "Nothing clears the row" is proved by ENUMERATION with positive
controls: exactly two production statements terminalize a pending row
(`reset.rs` `cas_terminalize`, `transition.rs` `terminalize_reset_request`), both
behind the seal, and `expiry_sweep.rs` never names the table.

**A fixture defect the control exposed.** `build_genuine_reset_request` signed
`idempotencyKey` as a fresh uuid, but production `parse_reset_authority` derives
a Reset REQUEST's operation id FROM `resetRequestId` and requires
`idempotencyKey` to equal it. Those otherwise-genuine bytes were unparseable by
`seal_pending_reset`. It went unnoticed because the only consumer consumed the
row through activation without re-parsing the request. Unrepaired, the control
could never have passed and the whole reproduction would have been
unfalsifiable — the wedge assertions would still have gone green, because the
drift check runs BEFORE the decode block. Repaired in the same lane;
`FROZEN_EXECUTOR_SEED_SHA256` re-pinned twice, each with its reason recorded at
the constant.

### Fix (a) — SHIPPED, sealed `87f7a7f8`

`ResetAuthorityBinding::RecordedForDisposal` is selected in exactly one place,
for a `Request` against a row where `trusted_instant >= row.expires_at`, and
skips exactly one comparison: the live device/key check. Every structural check,
the head-coordinate match, the recorded public-key hash, the signature
re-verification over the row's immutable bytes and the full equality battery all
still run, and the requester's device and key must still be present in the locked
scope at the recorded `key_id` and `enrollment_auth_generation`. A disposal
binding can mint EXACTLY `SealedResetTerminal::Expired`; every other shape
returns `GuardInvariant`.

**The hard constraint holds:** `activateReset` keeps FULL strict live-authority
verification, asserted at both a live and a lapsed instant. No sweeper composes
the seal. No privilege is created — actor authorization is upstream and untouched
(`reset.rs:2281`, before the row loads at `:2290`). No migration: the terminal
shape is the one the schema already defines for expiry.

Proven at the ENDPOINT, not only through the child-module probe. The probe
selects the binding itself, so alone it would show only that the seal accepts
one; a matched pair through `prepare_reset_request_authority` +
`expire_pending_reset_for_replacement`, differing only in the row's age, shows
that PRODUCTION selects it and drives the durable status to `expired`.

### Fix (b) — BLOCKED on a schema ruling. Finding 3 stays OPEN.

`revokeDevice` cannot terminalize a pending reset as ruled, because
`chat.reset_requests` offers no terminal that fits. `reset_requests_terminal_
shape_check` binds `stale`/`consumed` to a NON-NULL `terminal_transition_id`
(FK to `chat.transitions`), and a revocation has no transition; `expired` forces
`terminal_at = expires_at`, which would durably record a false expiry instant.
There is no `terminal_revocation_id` column.

The precedent makes the intended design plain: revocation already supersedes
neighbouring work through revocation-bound terminals
(`LeafRecoveryTermination::SupersededByRevocation`,
`ReservationTermination::ReleasedByRevocation`, written by
`write_revocation_bound_supersessions`), and `chat.leaf_recovery_requests`
carries `terminal_revocation_id` for exactly this. `chat.reset_requests` was
never given the equivalent. Recommended: a migration mirroring it, after which
(b) hooks into `apply_device_revocation_batch_prefix`
(`state_machine/executor.rs:5348`), the device-global stage. Reusing `expired` or
minting a synthetic transition were both declined as protocol-surface
inventions.

### What this means operationally

Fix (a) alone does not remove the wedge, it TIME-BOUNDS it. A conversation whose
reset requester is revoked or rebound is still completely unable to reset for up
to 24 hours, after which any active participant's `requestReset` disposes of the
row and recovery proceeds. The live-row wedge tests remain as
wedge-documentation and still pass; they flip only when (b) lands. When it does,
the revocation trigger should also be lifted to drive
`apply_device_revocation_batch_prefix` rather than the writers beneath it, or the
flip is vacuous.

## Addendum 2026-08-14 (fourth) — fix (b) schema landed; its Rust half blocked on the fixed-target ledger

Appended, not edited. Finding 3 is STILL NOT CLOSED. This records the approved
schema half of fix (b) landing, and a hard blocker on the Rust half that was
found by executing it, not by reading.

### Landed: the revocation-bound terminal (seal `a5338989`)

Josh approved the migration. `chat.reset_requests` now mirrors
`chat.leaf_recovery_requests`: a `terminal_revocation_id` column, a `revoked`
status whose shape requires it, and the composite FK
`(requester_did, requester_device_id, terminal_revocation_id, terminal_at)` →
`chat.device_revocations(target_did, target_device_id, revocation_id, accepted_at)`.
That FK is the structural guarantee — a reset request can only ever be
terminalized by ITS OWN requester's revocation.

Three things the same-seal tests forced that the design did not anticipate:

1. **`terminal_at IS NOT NULL` is load-bearing, not redundant.** A CHECK fails
   only on FALSE, so a bare `terminal_at >= received_at` evaluates NULL when
   `terminal_at` is NULL and the constraint ADMITS a revoked row with no terminal
   instant. The first version of the migration had that hole.
2. **The immutability trigger whitelists the exact mutable columns**, so the new
   column was unwritable until it joined the list — the CHECK admitted the shape
   and the BEFORE trigger then rejected the write as an identity change, making
   the new arm unreachable.
3. **No upper bound on `terminal_at`, deliberately.** A device may be revoked
   long after a pending request lapsed; binding `terminal_at <= expires_at` would
   make `revokeDevice` itself fail 23514 on exactly those rows.

### BLOCKED: the Rust half cannot land in this lane

The wiring compiles and is correct, but writing `terminal_revocation_id` fails
`42703` against every suite whose database is built from the reviewed migration
manifest in `tests/common/chat_protocol.rs` (via `tests/common/fresh_db.rs:362`).
Extending that manifest to 14 entries is refused by
`validate_exact_reviewed_ledger`: the shared clean-chat database is a **fixed
target** installed with exactly the reviewed 13 rows, and
`setup_chat_protocol_db` is validation-only by design — it "refuses migration or
repair". Re-installing the fixed target is a program-level act behind the
A0/A-final procedure and affects every concurrent lane, so it is not a lane's to
perform.

Measured, not assumed: with the manifest extended to 14,
`chat_protocol_transition_repository` goes 123/0/1 → 108/15/1.

The migration file alone is inert for those suites (it is not in the reviewed
manifest, so ledger-built databases ignore it) while per-run databases minted by
`sqlx::migrate!("./migrations")` pick it up — which is what makes the constraint
tests executable. Nothing regresses.

### The Rust half, ready to apply

Recorded here so it is not re-derived. Three edits, all verified to compile
(`cargo build` under `cfg(not(test))` clean) before being set aside:

1. `repository/transition.rs` — add to `ResetRequestTermination`:
   `SupersededByRevocation { terminal_revocation_id: Uuid, terminal_at: DateTime<Utc> }`,
   mapping in `terminalize_reset_request` to
   `("revoked", None, Some(terminal_revocation_id), terminal_at)`, with
   `terminal_revocation_id = $5` added to its UPDATE.
2. `repository/transition.rs` — a device-global writer
   `terminalize_reset_requests_for_revoked_device(tx, requester_did,
   requester_device_id, terminal_revocation_id, terminal_at) -> u64`, an UPDATE
   over `requester_did = $1 AND requester_device_id = $2 AND status = 'pending'`.
   Deliberately not a CAS on an expected row count: zero is the ordinary case,
   and the `status = 'pending'` predicate makes a replayed revocation idempotent.
3. `state_machine/executor.rs` — call it inside
   `apply_device_revocation_batch_prefix`, immediately AFTER
   `cas_registration_revoke`, so the revocation row and the revoked registration
   both exist when the deferred composite FK is checked.

### Withdrawn: the Rust half, on a defect it exposed

The three staged edits were applied exactly as recorded, `cargo build` was clean,
and the wedge harness's revocation trigger was lifted onto
`apply_device_revocation_batch_unscoped_for_test` (a `#[cfg(test)] pub(crate)`

conversations) so the flip would not be vacuous. That lift is what found this:

> **`load_reset_request_hydration_rows` cannot hydrate a `revoked` reset row.**
> `repository/core.rs:9081` matches the status against exactly `pending`,
> `stale`, `consumed`, `expired`, and returns `ResetLeaveHydrationError::
> OutOfDomain` for anything else. Its query has NO status predicate — it reads
> every row for the conversation.

So the moment fix (b) terminalizes a row to `revoked`,
`hydrate_locked_conversation_state` fails for that conversation permanently.
That hydrator has **13 call sites across 8 modules** including
`read_authority.rs`, `submit_transition.rs`, `revocation.rs`, `recovery.rs`,
`welcome_terminal.rs` and `expiry_sweep.rs`. Fix (b) as staged would convert
finding 3's 24-hour wedge into a PERMANENT, conversation-wide, total outage —
strictly worse than the bug it closes.

Observed, not only read: with the lift in place
`wedge_revoked_requester_drifts_the_seal_for_both_kinds` returns
`InvalidResetRow`, which `reset.rs:2520` maps from `ResetWork` alone. Code path
and runtime agree.

**Why it compiled.** The status crosses that boundary as a `String`, so nothing
typed catches it. This is the compile-clean/runtime-fatal shape the repo's own
guidance warns about; the fourth addendum's "verified to compile" was true and
insufficient.

### What Josh's ratification unblocked

`revoked` is the fifth reset-request status. The three staged writer edits alone
would have been catastrophic — see the sixth addendum — so the aggregate half
landed with them:

| edit | site |
|---|---|
| hydrator admits `revoked`, selects `terminal_revocation_id` | `repository/core.rs` |
| `ResetTerminalColumns` gains the column | `repository/core.rs` |
| `select_reset_terminal` gains a `Revocation` arm | `repository/core.rs` |
| `ResetTerminalSelection::Revocation` | `repository/core.rs` |
| `ResetRequestStatus::Revoked` | `state_machine.rs` |
| `reset_request_status_code` encodes it | `state_machine.rs` |

Three things the closure forced that the enumeration did not anticipate:

1. **There are TWO canonical encodings of this enum, not one.** Besides
   `reset_request_status_code`, `graph_digest_reset` in `core.rs` encodes the
   same statuses for the graph digest. The compiler found it; reading had not.
   Both now carry a note pointing at the other so they cannot drift apart.
2. **`validate_reset_work` needed a matching invariant arm** — a `Revoked` row
   must carry `WorkTerminalEvidence::DeviceRevocation` naming its own requester,
   at or after `received_at`, with no upper bound (a device may be revoked long
   after the request lapsed, which the DB check already allowed for).
3. **The projection outgrew a tuple.** With `terminal_revocation_id` it is 17
   columns and sqlx implements `FromRow` for tuples only to 16, so it became a
   named `FromRow` row.

Also tightened, deliberately: every OTHER arm of `select_reset_terminal` now
checks the revocation column too, so a shape the database would refuse can no
longer hydrate. `WorkTerminalLocator::DeviceRevocation` already existed from the
leaf-recovery precedent, so no new terminal shape was invented.

### What the digest-domain extension actually touches

The extension is **additive, never renumbered**: codes 1-4 are unchanged at both
encodings, so every digest over a row that is not `revoked` is byte-identical to
before. That is why the blast radius is as small as it is.

**In-repo fixtures needing regeneration: NONE.** Verified two ways rather than
assumed. First, no in-repo fixture carries a reset terminal status at all —
`mls_chat_contract_vectors.json` and `mls_chat_control_fingerprint_source.json`
both return zero matches for any reset terminal status literal, and the only
reset field either carries is `resetRequestId`, which is signed-request content
rather than server-derived terminal state. Second, empirically: every
digest-bearing suite passes with no fixture regenerated.

**Reaching the client-side control fingerprints: NOTHING, today.** The extended
codes feed `reset_hydration` / `graph_digest_reset`, which produce the aggregate
`durable_row_digest` — server-internal integrity. No handler references it, and
the control-entry fingerprints are computed over signed control bytes, which
never contain a server-assigned terminal status.
